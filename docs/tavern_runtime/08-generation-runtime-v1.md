# Generation Runtime v1

`TavernGenerationRuntime` is the application entry point. It depends on `TavernRepository` and a provider-independent `TavernGenerationDriver`; no Provider HTTP, Prompt Compiler, World Info runtime, tool executor, or production Tavern UI is connected. The future app composition root owns one app-scoped runtime for a repository scope, calls `recoverInterrupted()` once before accepting commands, and awaits `dispose()` at shutdown. UI pages and Provider adapters must not create their own lifecycle owners or invoke recovery. The current phase has no production Tavern composition root.

Commands carry stable Session, Story Line, Turn, Alternative and Attempt IDs. Normal Reply requires the latest player Turn and atomically creates a character Turn, first Alternative and Attempt. Retry creates only an Attempt on a failed/cancelled Alternative. A Retry of a failed Continue keeps the `continueTurn` attempt type so earlier completed content remains in the transcript; other Retry attempts use the Foundation `regenerate` type. Regenerate creates a new Alternative and first Attempt atomically, retaining the previous selection until the new response completes. Continue creates an Attempt on the selected Alternative. The Foundation `alternative` type represents New Answer. Runtime command kind remains explicit so callers do not confuse the operations.

Text and reasoning deltas remain separate typed Content Parts. Consecutive deltas of the same kind are batched to a bounded character threshold, and partial batches flush on cancel, failure or completion. The handle emits transient state updates for UI subscriptions. Canonical content and Attempt status are persisted through repository methods; the UI never polls SQL and the driver never mutates Tavern domain state. Completion atomically persists the final batch and terminal status. Regenerate and Retry may auto-select their completed Alternative only when the selected Alternative still matches the one observed at start; the repository makes this comparison in the same transaction as finalization. Normal Reply is already selected by its atomic creation. Continue never changes selection and always writes to its original target Alternative. Failed/cancelled partial Parts remain available to inspection but are omitted from normal transcript projection. Completed Continue Attempts append to prior successful content without flattening provenance.

The v13 schema and archive format remain unchanged. Existing archive roundtrip covers failed, cancelled, completed, reasoning, typed Parts and branch lineage. No Legacy World, Novel, Chat or Plugin repository is imported by this runtime.

## Known limits

- One active generation per Session is enforced across Runtime instances in the same process. The repository supplies a scope key (SQLite database path or in-memory repository identity) to a shared in-process registry. This is a defense against accidental duplicate Runtime construction, not a substitute for app-scoped lifecycle ownership. Cross-process locking and background multi-process generation are not provided.
- Command IDs are deduplicated in the live process with a bounded recent cache; callers must use stable IDs and must not reuse one ID for another target. A duplicate after cache eviction fails at Foundation identity constraints rather than creating a second Turn.
- A future Provider adapter must implement its own transport cancellation and normalize errors/events. This phase uses deterministic fake streams only.
- Tool Call/Result remain typed Foundation data; the generation driver contract does not yet accept or execute tool calls.
- No Prompt Compiler is present, so the driver contract deliberately receives target identity, not a compiled prompt. Prompt compilation and Provider adaptation are prerequisites to real chat.
